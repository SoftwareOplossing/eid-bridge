# Let's Peppol Web eID + Bundled Belgian eID Middleware
## Implementation and Validation Plan

**Project goal:** Build a Let's Peppol-specific Web eID distribution that lets a Belgian user complete the existing Let's Peppol KYC flow after installing **one package instead of two**, by bundling the required Belgian eID PKCS#11 runtime with the Web eID native application.

**Primary PoC target:** Windows 10/11 x64 + Chrome/Edge + common Belgian USB CCID reader + Belgian eID card.

**End state:** A maintained, security-reviewed installer that contains the Let's Peppol Web eID native bridge and the minimum required Belgian eID middleware components, supports the browsers and operating systems Let's Peppol chooses to support, and demonstrably satisfies the current KYC requirements.

---

# 1. Executive summary

The proposed architecture is:

```text
Let's Peppol web application
        |
        | web-eid.js
        v
Web eID browser extension
        |
        | Native Messaging
        v
Let's Peppol Web eID native application
        |
        | PKCS#11
        v
Bundled Belgian eID PKCS#11 module
        |
        | PC/SC
        v
Operating-system smart-card service
        |
        v
USB CCID card reader
        |
        v
Belgian eID
```

The important architectural decision is that the Let's Peppol package should **not initially replace the Belgian smart-card implementation**. It should reuse the official Belgian eID middleware's PKCS#11 implementation and make it private to the Let's Peppol application wherever practical.

The PoC must prove four things independently:

1. **Bundling:** Web eID can load a privately bundled `beidpkcs11` module without requiring the normal Belgian eID middleware installation.
2. **Card operations:** The bundled module can retrieve the Belgian signing certificate and perform a PIN-protected signature through a normal USB card reader.
3. **KYC identity:** Let's Peppol can obtain and validate the identity information required by the current KYC process from trusted signed/certificate data.
4. **Deployment:** A clean Windows machine can complete KYC after installing one Let's Peppol package, with no separate Belgian eID middleware installation.

Only after all four are proven should packaging, branding, automatic updates, Linux/macOS support, and production rollout begin.

# 2. Current assumptions that must be verified

Codex must treat these as hypotheses, not facts.

## H1. Web eID can use the Belgian eID through PKCS#11

Upstream Web eID supports PKCS#11-backed cards through `libelectronic-id`. Recent Web eID release activity also mentions Belgian eID fixes. Before implementing anything, inspect the current upstream repositories and determine:

- whether Belgian eID card detection already exists;
- whether Belgian eID is considered a PKCS#11-backed card;
- which PKCS#11 library names/paths are currently expected;
- whether the path is compile-time, runtime-configurable, registry-based, or hard-coded;
- whether multiple Belgian card generations are supported;
- which operations already work:
  - authentication;
  - `get-signing-certificate`;
  - `sign`.

**Do not duplicate existing Belgian support.**

## H2. `beidpkcs11.dll` can operate as an application-private DLL

Prove whether the official PKCS#11 DLL can be copied next to the Let's Peppol Web eID executable and loaded explicitly without the normal Belgian eID installer having run.

Determine all transitive runtime dependencies.

Possible outcomes:

- **Best:** the DLL and ordinary Windows smart-card service are sufficient.
- **Acceptable:** a small set of additional LGPL/runtime DLLs must be bundled.
- **Problematic:** the middleware requires machine-wide registry entries, minidriver registration, services, or other installation state.
- **Go/no-go issue:** the PKCS#11 implementation cannot function reliably as an application-private component.

Do not infer this from source code alone. Test it on a clean VM.

## H3. Let's Peppol's current KYC identity requirement can be fulfilled

Document the exact present KYC requirement before changing the implementation.

At minimum, determine whether the system currently requires:

- legal first name;
- legal surname;
- Belgian national registry number;
- date of birth;
- signing certificate subject;
- authentication certificate subject;
- proof that the cardholder controls the eID private key;
- proof that the signed PDF is the exact PDF generated by Let's Peppol.

Do not expand the amount of personal data collected merely because the card exposes it.

## H4. Bundling is legally redistributable

The Belgian eID middleware is published under LGPL-3.0-or-later.

Before release, document:

- exact upstream version/commit used;
- exact binary built or redistributed;
- corresponding source availability;
- required copyright and license notices;
- mechanism allowing replacement of the LGPL component where legally required;
- whether the Let's Peppol installer modifies the upstream component;
- whether dynamically linking from the Let's Peppol application preserves the intended separation.

This is an engineering compliance task, not legal advice. Flag anything ambiguous for legal review.

# 7. Stage 2 - Minimal private-DLL PoC

## Objective

Prove the central assumption:

> Web eID can use a bundled Belgian PKCS#11 module without installing the Belgian eID middleware.

This stage is intentionally ugly. No installer. No branding. No automatic detection beyond what is necessary.

## Environment

Create a clean Windows 11 x64 VM snapshot with:

- Chrome;
- Edge;
- Web eID extension as required for development;
- normal Windows smart-card service;
- USB pass-through or a physical test machine;
- card-reader driver if Windows does not provide it automatically;
- **no Belgian eID middleware**.

Verify before testing that:

```text
beidpkcs11.dll
```

is not present in the ordinary middleware location.

## Tasks

1. Obtain/build the official x64 `beidpkcs11.dll`.
2. Copy it into a private test directory, for example:

```text
C:\LetsPeppolPoC\
  web-eid.exe
  beidpkcs11.dll
  ...
```

3. Determine all dependent DLLs with tooling such as:
   - `dumpbin /DEPENDENTS`;
   - Dependencies.exe;
   - Process Monitor;
   - loader diagnostics.
4. Modify the minimum possible Web eID / `libelectronic-id` code so Belgian PKCS#11 is loaded via an explicit application-private path.
5. Do **not** modify PATH or copy the library to `System32`.
6. Do **not** register Belgian middleware globally.
7. Add diagnostic logging that records:
   - module path;
   - module load success/failure;
   - PKCS#11 initialization;
   - token/slot detection;
   - card detection;
   - certificate detection;
   - operation status.

Never log:

- PIN;
- private keys;
- full national registry number;
- sensitive raw identity contents.

## Required tests

### POC-1: Load module

From a machine without Belgian middleware installed:

```text
LoadLibrary(private beidpkcs11.dll)
```

must succeed.

### POC-2: Enumerate token

With reader + card attached:

- initialize PKCS#11;
- enumerate slot/token;
- identify Belgian eID.

### POC-3: Retrieve signing certificate

Call Web eID:

```text
get-signing-certificate
```

Success criteria:

- correct certificate is returned;
- certificate can be parsed;
- subject belongs to the inserted Belgian eID;
- no system-wide Belgian middleware is installed.

### POC-4: Sign controlled data

Call Web eID signing using a known SHA-256 digest.

Success criteria:

- PIN prompt appears;
- correct PIN succeeds;
- wrong PIN is rejected;
- returned signature verifies with the certificate public key.

### POC-5: Reader removal

Remove card before/during operation.

Application must fail safely and recover after reinsertion.

## Go/no-go gate A

Proceed only if POC-1 through POC-4 work on a clean Windows installation.

If they do not work, determine whether missing requirements are:

- harmless private dependencies that can be bundled;
- Visual C++ runtime requirements;
- registry configuration;
- Windows smart-card/minidriver requirements;
- machine-wide middleware requirements.

If machine-wide Belgian middleware installation remains necessary, document why. Do not fake success by silently installing the full middleware.

# 8. Stage 3 - Prove Let's Peppol KYC end-to-end

## Objective

Prove that the private PKCS#11 runtime satisfies the actual business/security requirement, not merely that `C_Sign()` returns bytes.

## Environment

Clean Windows VM:

```text
Let's Peppol PoC package
+
browser
+
reader
+
Belgian eID
```

No separately installed Belgian eID middleware.

## Test flow

### KYC-1: Retrieve certificate

The browser requests the signing certificate through Web eID.

Server/client verifies it is the intended certificate type.

### KYC-2: Generate PDF

Let's Peppol generates the exact same KYC PDF as production/staging currently generates.

Record:

- original document hash;
- signing algorithm;
- signing certificate fingerprint.

### KYC-3: User signature

Use Web eID + bundled `beidpkcs11`.

User enters the PIN only in the trusted native UI.

The website must never receive or handle the PIN.

### KYC-4: Final PDF validation

Backend verifies:

- signed content equals the intended document;
- signature cryptographically verifies;
- signing certificate is trusted;
- certificate validity period;
- relevant certificate policy/EKU/key usage;
- revocation status if required by current KYC;
- signer identity extracted from trusted certificate/card data;
- signer name satisfies current Let's Peppol KYC matching rules.

### KYC-5: Tamper tests

Verify rejection if:

1. PDF changes after signing.
2. Signature bytes change.
3. Certificate is replaced.
4. challenge/session identifiers are replayed.
5. certificate comes from an untrusted CA.
6. user attempts to reuse a signature from another KYC transaction.
7. frontend submits a name different from the certificate/card identity.
8. signing occurs for a different document digest.

## Deliverable

`docs/kyc-validation-report.md`

Use a table:

| Test | Expected | Result | Evidence |
|---|---|---|---|
| clean KYC | accepted | | |
| altered PDF | rejected | | |
| replay | rejected | | |
| wrong identity | rejected | | |
| invalid certificate | rejected | | |

## Go/no-go gate B

Do not start production packaging until the bundled implementation produces the same or stronger KYC assurance as the existing implementation.

# 10. Stage 5 - Fork strategy

## Objective

Minimize permanent divergence from upstream Web eID.

Prefer:

```text
upstream Web eID
    +
small Let's Peppol patch
    +
packaging changes
```

over a heavily rewritten fork.

## Required fork policy

1. Add upstream repositories as remotes.
2. Document base tag/commit.
3. Keep Let's Peppol changes in isolated commits.
4. Avoid renaming internal APIs unnecessarily.
5. Preserve Web eID's native messaging protocol where possible.
6. Keep `web-eid.js` compatibility where possible.
7. Make Belgian module path resolution configurable/testable.
8. Write automated tests for every fork-specific change.
9. Maintain an `UPSTREAM.md` with rebase/update instructions.

## Preferred implementation pattern

Introduce something similar to:

```text
Pkcs11ModuleResolver
```

with platform-specific resolution:

```text
1. Let's Peppol private runtime directory
2. optionally supported system installation
3. fail with actionable error
```

For the Let's Peppol package, the private runtime should be deterministic.

Avoid DLL search-path ambiguity.

On Windows, prefer explicit absolute-path loading or a securely constrained DLL directory rather than relying on the process working directory.

## Security requirement

Prevent DLL preloading/hijacking.

The implementation must not search user-writable directories for PKCS#11 modules.

# 12. Stage 7 - Browser extension strategy

## Objective

Decide whether Let's Peppol needs its own Web eID browser extension or can use the upstream extension.

Investigate first.

### Option A - Reuse upstream Web eID extension

Preferred if the native messaging application name/protocol can remain compatible and the distribution model permits it.

Advantages:

- less code;
- established extension;
- fewer extension-store review/update obligations.

Risk:

- upstream extension may require the upstream native application identity;
- Let's Peppol-specific installer may conflict with official Web eID installation;
- future upstream updates may break assumptions.

### Option B - Let's Peppol-branded fork of the extension

Use only if necessary.

Requirements:

- unique extension/application IDs;
- strict origin allowlist where practical;
- Let's Peppol production/staging/dev origin handling;
- Chrome Web Store / Edge Add-ons / Firefox AMO distribution strategy;
- no arbitrary websites allowed to invoke the Let's Peppol native application.

## Security test

A random origin such as:

```text
https://example.org
```

must not be able to trick the Let's Peppol bridge into signing arbitrary content if origin restrictions are part of the chosen design.

# 13. Stage 8 - Security review

Create `docs/threat-model.md`.

At minimum cover:

## Assets

- eID private signing key;
- PIN;
- identity attributes;
- KYC document;
- signature;
- certificate;
- Let's Peppol account/KYC session.

## Trust boundaries

```text
website
<-> browser library
<-> extension
<-> native messaging
<-> native application
<-> PKCS#11
<-> PC/SC
<-> smart card
```

## Threats

- malicious website invoking extension/native app;
- origin spoofing;
- replayed signing requests;
- signing a different document than displayed;
- substitution of PKCS#11 DLL;
- DLL search-order hijacking;
- malicious local user replacing bundled DLL;
- compromised extension update;
- compromised native application update;
- stale/expired/revoked certificate;
- PIN capture;
- excessive identity-data collection;
- logging sensitive card data;
- downgrade to vulnerable bundled middleware;
- tampered installer;
- unsigned executable;
- MITM during software update;
- cross-account KYC replay.

## Required properties

1. PIN never leaves native/card interaction.
2. Private key never leaves eID.
3. User consent occurs immediately before signature.
4. Backend treats client-provided identity as untrusted until cryptographically validated.
5. Backend binds signature to a unique KYC transaction.
6. PKCS#11 binary authenticity is controlled.
7. Installer and application binaries are code-signed for production.
8. Updates are authenticated.
9. Sensitive logs are minimized.

# 25. Abort conditions

Stop and escalate instead of engineering around the problem if any of these are discovered:

- private `beidpkcs11` loading requires unsafe DLL search behavior;
- the official module requires substantial undocumented machine-wide installation;
- KYC identity can only be obtained from unauthenticated client-controlled data;
- PIN must cross into browser JavaScript;
- bundling violates a license obligation that cannot reasonably be satisfied;
- current Web eID Belgian support is unstable for production card generations;
- the modified flow weakens server-side signature or identity validation;
- installer coexistence breaks official Belgian eID software.

The goal is one installation, not one installation at the cost of making identity verification worse.

# 26. Useful upstream facts to validate against current source

As of the planning date:

- Web eID uses a browser extension plus a native application and Native Messaging.
- The native application exposes operations including authentication, retrieving the signing certificate, and signing.
- `libelectronic-id` supports direct PC/SC cards and PKCS#11-backed cards.
- Web eID's architecture explicitly allows PKCS#11 for cards whose direct APDU protocol is not implemented.
- The official Belgian eID middleware provides a PKCS#11 implementation and custom-application SDK.
- The Belgian eID middleware repository is LGPL-3.0-or-later.
- The official Windows installer contains separate 32-bit and 64-bit `beidpkcs11.dll` builds.
- Recent Web eID release history mentions Belgian eID support fixes, therefore current upstream behavior must be inspected before adding new Belgian-specific code.

These are starting points only. Pin current upstream source and record what is actually true at implementation time.

# 27. Final architectural target

If the PoC succeeds, the preferred Windows architecture is:

```text
+-------------------------------------------------------+
| Browser                                               |
|                                                       |
| Let's Peppol KYC -> web-eid.js -> Web eID extension |
+----------------------------+--------------------------+
                             |
                       Native Messaging
                             |
                             v
+-------------------------------------------------------+
| Let's Peppol eID installation                         |
|                                                       |
| letspeppol-web-eid.exe                                |
|        |                                              |
|        +--> private beidpkcs11.dll                    |
|                    |                                  |
+--------------------|----------------------------------+
                     |
                    PC/SC
                     |
                     v
              USB CCID reader
                     |
                     v
               Belgian eID
```

Server-side KYC remains authoritative:

```text
Signed KYC document
        |
        v
Let's Peppol backend
        |
        +--> verify document integrity
        +--> verify signature
        +--> validate certificate chain/status
        +--> derive trusted signer identity
        +--> match signer to KYC/account
        |
        v
KYC accepted/rejected
```

The native installer changes **how the card is reached**, not what the Let's Peppol backend trusts.

# 28. Initial milestone

The first milestone is deliberately narrow:

> On a clean Windows 11 x64 machine without the Belgian eID middleware installed, a locally built Web eID application must load a private `beidpkcs11.dll`, retrieve the signing certificate from a Belgian eID, sign a known digest after PIN entry, and produce a signature that verifies independently.

Do not begin installer work until this milestone passes.

That single experiment decides whether the proposed architecture deserves further investment.
